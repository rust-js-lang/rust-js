# 0329. A `Pin` is its pointer

Status: Accepted. Extends [0023](0023-strings-references-shared-state.md)
and [0099](0099-mut-references.md); counted by
[0314](0314-std-data-structures.md).

Case: A ([0262](0262-when-rust-and-js-disagree.md)).

## Context

`Pin<P>` promises that what `P` points at never moves again. `Box::pin`,
`Pin::new` and every `Pin` method were errors, and so was a method of
`self: Pin<&mut Self>`, as futures and self-referential types write them.

## Decision

**A `Pin<P>` is `P`, and its functions are its pointer's.** JS never moves
a value, so what a `Pin` promises is kept already.

```rust
let mut pinned = Box::pin(5);
pinned.set(6);
let mut number = 7;
let mut pin = Pin::new(&mut number);
*pin += 1;
```

```js
let pinned = 5;
pinned = 6;
let number = 7;
const pin = {
  get value() {
    return number;
  },
  set value(value) {
    number = value;
  },
};
pin.value = (pin.value + 1) | 0;
```

| Rust | JS |
|---|---|
| `Box::pin(x)`, `Box::into_pin(b)`, `Pin::new(p)`, `into_inner`, `get_ref` | the same value |
| `*pin`, `as_ref()`, `into_ref()` | what it points at: a pinned `&mut` to a number or text its box's `value` |
| `as_mut()`, `get_mut()`, `DerefMut` | its pointer, a box for a number or text (ADR 0074) |
| `pin.set(v)` | what it points at written: `pin.value = v`, or `$assign(pin, v)` of an object a `&mut` points at (ADR 0147) |
| `map_unchecked(f)`, `map_unchecked_mut(f)` | `f(pin)` |

- **Everywhere a `Box` is its value, a `Pin` is its pointer**: a `&mut` to
  one, an `Option` of one, `{}` and `{:?}`, `==`, `<`, a clone and a drop.
- **A `&mut` to a `Pin` of a reference is the pin**, as only what it points
  at is changed through it.
- **`==` looks through a `Box`, an `Rc` and a `Pin`**, so a hand-written
  `eq` of a unit struct inside one runs. It was skipped: `Box::new(Any) ==
  Box::new(Any)` was `undefined == undefined`.
- **Still refused**: `as_deref_mut`, which is unstable.

## Why

- **It's the same program**: nothing in JS moves, so each read and write
  through a `Pin` is its pointer's.
- **It's the JS a person writes**: a pinned box is its value.
- **It's tested**: the `pin_box` corpus case runs `Box::pin`, `set`, a
  `self: Pin<&mut Self>` method, `Pin::new` of `&` and `&mut`, `*pin += 1`,
  `map_unchecked` and `map_unchecked_mut`, `{}` and `{:?}`, `==`, `<`, a
  clone changed after, a pinned value with a destructor, and a unit
  struct's own `==` in a `Pin` and a `Box`, against native Rust. Mutations
  read a pinned `Box` as its box, show a pinned box, skip `f`, assign a
  number as an object, box a pinned `&mut` again, and compare as constants.
- `docs/std-coverage.txt`: `Pin` 15 of 16, `Box` 4 of 17.

## Amendment (2026-11-12, #1446, #1435): a `Pin` compares, orders and hashes its target

Case ([0262](0262-when-rust-and-js-disagree.md)): results changed, so Rust's
behavior is kept. std's `PartialEq`, `PartialOrd`, `Ord` and `Hash` of a
`Pin<Ptr>` are its target's, `Ptr::Target::eq(self, other)`, never the
pointer's own. A `Pin` is its pointer in JS, and rust-js compared that: right
of a reference, a `Box` or an `Rc`, which are their target and compare as
it, but of the crate's own smart pointer, whose own `==`, `cmp` and `Hash`
may read more than its target, wrong. `Pin::new(Tagged { key: Key(7), tag: 1
}) == Pin::new(Tagged { key: Key(7), tag: 2 })` was `false` where Rust's is
`true` (#1446, P0), and a hash set of such pins kept both (#1435, refused
before #1289's message named it).

**One owner says what a `Pin` reads: `pinned_target`** (recognition/wrappers.rs).
Of a reference or one of std's pointers, a `Box`, an `Rc`, an `Arc`, a
`String`, a `Vec`, whose own `==`, order and `Hash` are its target's, the
pointer; of the crate's own pointer, its `Deref` target, read by its
`deref()`, `holderDeref_deref(h)`. `pin_target` and `own_deref`
(std_types/pin.rs) read it for `==` (`eq_value`), `!=` (`ne_value` and
`own_ne_in`, a target's own `ne` called), `<` and `cmp` (`cmp_value`) and
`Hash` (`Hashed::Target`, ADR 0463). A `Pin<String>` now hashes as its
`String`, where it was refused.

Still refused, each naming #1448: a read through a `Pin` of a pointer
other than a reference or a `Box`, `*p.as_ref()` of the crate's own, and
`Rc::pin`. The map's refusal of a key whose `Hash` rust-js doesn't write is
now a std type's, a `Duration`'s, and names #1447, as the missing `Hash` of
one does (`open_evidence`, recognition/open_calls.rs); and a `Wrapping`'s or
a `Saturating`'s `sum()` names #1445.

Held by corpus case `pins_compare_and_hash_their_targets.rs` (a pointer
whose own `==`, `cmp` and `Hash` read a tag its target hasn't: `==`, `!=`,
`<`, `cmp`, `partial_cmp`, `max`, a hash set and map, a B-tree set; and
`Pin<Box>`, `Pin<&>`, `Pin<Rc>`, `Pin<String>`, `Pin<Vec>`), and the `Pin`
lines of `own_ne_max_min_clamp.rs`, against native Rust in both builds;
diagnostics rows of #1445, #1447 and #1448. Mutations
`pin-of-own-pointer-compared-as-it`, `pin-of-std-smart-pointer-dereffed`,
`pin-ne-unknown`, `pin-of-any-pointer-hashed-as-it`, `std-hash-evidence-unnamed`,
`newtype-sum-unnamed`, `rc-pin-unnamed`, and `eq-of-pin-as-constant`,
`pin-cmp-unknown`, `box-ne-not-its-value`, `pin-hash-unwritten` refitted.
