# 0272. Node's modules are a crate of their own, typed as @types/node

Status: Accepted. Follows [0024](0024-web-crate.md) and
[0192](0192-next.md).

Case: N ([0262](0262-when-rust-and-js-disagree.md)).

## Context

react.dev's errors page reads its Markdown in Next.js's `getStaticProps`,
which runs in Node:

```tsx
const fs = require('fs');
const rootDir = process.cwd() + '/src/content/errors';
mdx = fs.readFileSync(rootDir + '/' + path + '.md', 'utf8');
```

The builtins crate is JS's language, and webapi the browser's, from
WebIDL. Node's modules are in neither, and a port's own bindings for them
would hide that rust-js lacks them.

## Decision

**The `node` crate, `rust-js-node`, is Node's modules, hand-written as the
builtins crate is, typed as `@types/node` types them, one binding at a time
as ports need them.** Its first:

- `fs::read_file_sync(path, encoding)` is `readFileSync(path, encoding)`,
  imported from `fs`, a `Result` of what it throws (ADR 0035): a missing
  file is routine, as the page's `catch` has it.
- `process::cwd()` is `process.cwd()`, `process` a global.
- `BufferEncoding` is `@types/node`'s, each variant its string, `"utf8"`.

`node/build.sh` builds its metadata, as `webapi/build.sh` does.

## Why

- **It's the JS a person writes in Node**: an import of `fs`'s, which
  Next.js leaves out of a page's client bundle with `getStaticProps`.
- **`@types/node` is what a TypeScript program has**, as the react crate
  follows `@types/react`.
- **Hand-written, not generated**: `@types/node` is TypeScript, overloads
  and all, not WebIDL; a generator is worth it when ports need much of it.
- **It's tested**: a compiler test reads a file, a missing one, and the
  directory it runs in.

## Alternatives

- **Generate it from `@types/node`**, as webapi is from WebIDL: all of
  Node, but a TypeScript reader's work before the port moves.
- **The port's own bindings**: what rust-js lacks would stay lacking.

## Amendment: `http`'s request and response

`node::http` (2026-10-10) binds `IncomingMessage` and `ServerResponse`,
what a server's handler is given, and what Next.js's Pages Router gives
`getServerSideProps` and an API route: a request's method, URL, headers
and version, and a response's status, headers, `write` and `end`. Each is
an instance, its members bound by their names, so no module is imported.
Their streams' events aren't bound yet. A bindings test serves a fetch
with a handler of them.

## Amendment: hand-written, module by module, by one set of rules

Generating it was weighed again and set aside (the user's choice,
2026-10-10): hand-written, with `node/coverage.txt` (ADR 0351) saying
what's done and what's left. Hand-written bindings drift, as ReScript's
Node bindings do (their `stat` calls `lstat`), so each module is bound by
webapi's rules and a bindings test runs each binding against Node's own:

- **A module's value is its named import**, `path#join`, also of an
  `export =` object's members, as Node's ESM gives them; a constant or an
  object of one is a `static`, `path::sep`, `path::win32`.
- **An optional parameter is a `_with_` form**, `basename_with_suffix`,
  named as webapi names one (ADR 0024); a rest parameter a slice,
  `#[rust_js::variadic]` (ADR 0221).
- **An interface given is a struct of `Option`s with `Default`**,
  `FormatInputPathObject<'a>`; one returned, of owned fields,
  `ParsedPath`; an object with methods, a handle, `PlatformPath`.

`path` (2026-10-10) is the first bound whole, 19 of 19.

`url` (2026-10-10): 17 of 24. Its WHATWG classes, `URL`,
`URLSearchParams` and `URLPattern`'s, are the globals, so the crate
re-exports webapi's (it now depends on webapi) and binds the rest: file
URLs, domains, `resolve`, `format` of a `URL`. Its legacy `parse` and
`Url` wait for `querystring`, `fileURLToPathBuffer` for `Buffer`, and
`urlToHttpOptions` for `http`'s `ClientRequestArgs`.
