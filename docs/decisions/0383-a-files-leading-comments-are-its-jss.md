# 0383. A file's leading comments are its JS's

Status: Accepted. Extends [0018](0018-print-with-oxc.md). Extended by
[0444](0444-a-comment-is-where-its-code-is.md): every other comment is the
JS's too, where its code is, by the same rules for what JS can hold.

Case: N ([0262](0262-when-rust-and-js-disagree.md)): comments, which
nothing runs.

## Context

A file moved to Rust keeps what it starts with, react.dev's license:

```rust
/*
 * Copyright (c) Meta Platforms, Inc. and affiliates.
 * ..
 */
```

Its JS had rust-js's line alone, `// Generated by rust-js from ..`: the
license the file it replaced had was gone from the file the app ships.

## Decision

**The comments a Rust file starts with, `//` and `/* */`, up to its first
doc comment, attribute or item, are its JS's, after rust-js's line, as
written.**

```js
// Generated by rust-js from src/components/ExternalLink.rs. Do not edit.

/*
 * Copyright (c) Meta Platforms, Inc. and affiliates.
 * ..
 */
```

- **A doc comment is its item's or its module's**: `///`, `//!`, `/**`
  and `/*!` end them, as Rust reads them; `////`, `/***` and `/**/` are
  plain, as Rust reads them too.
- **A block comment Rust nests**, `/* a /* b */ c */`, which JS ends at its
  first `*/`, ends them.
- **A line comment JS would end early**, at a carriage return but a
  CRLF's, at U+2028 or U+2029, where Rust's goes on, ends them: its rest
  would be code. rustc's lexer tests have one.
- A module's `.d.ts` has them too, after the same line.
- A `/** .. */` license, a TypeScript file's, is `/* .. */` in Rust, where
  `/**` documents the item after it: its JS is `/* .. */`.

## Amendment: a run right above the first code is its (ADR 0625)

A run of comments right above the first code, no blank line between, is
that code's, where a blank line parts it from what the file starts with:
the license stays the header.

## Amendment: a blank line inside a block comment parts nothing (#312)

A run of comments right above the code is the code's, parted from the
file's at the last blank line (ADR 0444): that blank line was found
anywhere in the comments, so one inside a block comment, TheAlgorithms/
rust's PCG32's `/* Permuted Congruential Generator\n\nNote that .. */`,
cut it there, and rust-js wrote an unterminated `/*` it couldn't read
back. **Only a blank line between two comments parts them**; a block
comment is one, whole. Held by `comments::tests`, the lowering test "a
file's block comment with a blank line in it is one comment" and the
mutation `head-comment-cut-inside-a-comment`.


## Amendment: leading comments right above the code (2026-10-30, #419)

A file's leading comments are its JS's header, then a blank line, then
its imports and code. Where the source has no blank line between them and
its first item, and the module imports nothing, that blank line is the
JS's alone: React's generated `ReactDOMFizzInstructionSetInlineCodeStrings`
writes `// This is a generated file.` right above its first `export`.
**Of a module that imports nothing and has no directive, leading comments
right above its code (`Module::header_on_code`, what `output.rs` reads of
the source after them) are right above its JS too, no blank line.** A
module with imports keeps them after a blank line, as the corpus's files,
whose first comments are right above their `use`s, describe the file.
A block comment right above the code, TheAlgorithms' PCG32's (#312), is
right above its JS so too. Held by `lowering-comments-items`'s "leading
comments right above the code are right above its JS", `lowering-comments`'
PCG32 test, and the mutation `header-on-code-spaced`
(`to_oxc/header.ts`); no corpus case changes.
