# A shipped crate preserves its Rust API's contract

Status: Draft. Would extend [0415](../0415-a-crate-of-crates-io-in-an-app.md)
and [0423](../0423-hashbrowns-maps-are-stds.md), while preserving
[0407](../0407-a-raw-pointer-is-a-handle-on-its-place.md)'s refusals where
addressable-memory behavior cannot be represented.

Case: C ([0262](../0262-when-rust-and-js-disagree.md)) for observable API
behavior; A only for implementation details proven unobservable; D for
unsupported APIs or inputs. A platform API with a similar name is not
proof of equivalence.

## Context

Some crates use pointer operations rust-js cannot currently represent.
Reimplementing an appropriate API over JS primitives can preserve its
meaning without reproducing its memory engine. hashbrown establishes a
precedent for recognition, not proof that every other crate can be
replaced faithfully.

The earlier proposal treated regex, memchr and url as one decision and
their doc examples as sufficient evidence. Their contracts differ:
regex exposes Unicode and byte-offset behavior, memchr searches bytes,
and url exposes parsing, serialization and mutation semantics.

Nor is every pointer refusal permanent: extending the pointer model may
close one. A decision to replace a crate needs evidence about that crate,
not the claim that no compiler change could ever support it.

## Decision

**Qualify each shipped implementation against one explicit Rust crate
contract. Keep rustc's original types and checks; recognize supported
items once and lower them to the qualified implementation. Refuse
everything outside that contract.**

The initial candidates have separate proposals and acceptance gates:

- [memchr](shipped-memchr.md): byte scanning without pointer arithmetic.
- [regex](shipped-regex.md): a validated pattern language and matching
  contract; delegation to `RegExp` needs proof.
- [url](shipped-url.md): parsing and mutation over qualified URL behavior.

Accepting one does not accept the others, `regex-automata`, powerfmt, or
their dependents. Start with memchr's bounded API. Do not forecast an
increased crate-corpus count before the relevant probes pass.

### One owner at each boundary

- **Cargo owns the shipped-crate catalog.** Extend the existing catalog,
  rather than add another list. Each entry identifies supported package
  identity, versions/features and implementation artifact. Hosts and
  packaging consume that catalog.
- **Recognition owns item mapping.** Resolve checked definitions from
  the qualified crate identity. A matching package name or item path
  alone cannot authorize replacing a modified path dependency or fork.
  Unsupported identities are refused with an actionable diagnostic.
- **The implementation owns API behavior.** Original registry types
  remain rustc's authority. Internal bindings adapt their calls to the
  implementation; application code needs no replacement imports or
  stand-in types. Generic calls, methods as function values, traits and
  associated types must follow the same recognition path.
- **Artifacts record the contract.** Cache keys and manifests include
  the qualified crate source/version, enabled features, compiler/runtime
  identity and implementation version. Reject mismatches, including in
  transitive dependencies and the browser compiler.

A shipped implementation replaces the selected crate as a compilation
unit. An unrecognized reachable item is a compiler error, never an
attempt to compile an arbitrary leftover fragment of the original crate.
An unsupported feature combination is refused before publication.

### Errors are part of the contract

An invalid input recognized by Rust returns the same kind of Rust error.
A valid input outside the implementation's support is a rust-js refusal,
not a fabricated Rust parse error or a panic that `catch_unwind` can
mistake for the crate's behavior.

Reject statically known unsupported input at compile time. Where only
execution can reveal it, use ADR 0262's explicit runtime refusal, before
performing the unsupported operation. The per-crate proposal must define
that distinction for dynamically constructed inputs.

## Acceptance

For each crate, maintain a supported API/feature matrix and test each row
against native Rust at the qualified version. Include boundaries,
invalid inputs, generic and cross-crate uses, aliases and mutation,
Unicode where relevant, and supported browser/native runtime environments.
Use upstream tests where applicable, differential generated cases, and
mutations that produce plausible wrong answers. A single corpus probe
is an integration smoke test, not the complete conformance suite.

Verify that unsupported items, versions, modified sources and features
fail clearly without partial output. Inspect the generated JS and measure
runtime cost, generated bytes and any promised resource bounds.
Hold catalog ownership and recognition boundaries in architecture tests.

## Alternatives and consequences

Extending the pointer model remains appropriate where it preserves the
program naturally. A separate linear-memory engine would need its own
representation and interop decision; it is not an implicit fallback.
Exclusion remains honest when a faithful implementation is not available.

Every shipped crate creates an ongoing compatibility obligation. Major
version alone is not sufficient qualification: compatible Rust releases
may change observable details or features the implementation must track.
Update support claims only from evidence at the release being shipped.
